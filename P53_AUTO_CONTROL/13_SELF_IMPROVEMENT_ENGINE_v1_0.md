# IVDIVO — CONTROLLED SELF-IMPROVEMENT ENGINE v1.0

**STATUS:** CURRENT MANDATORY LEARNING LOOP

## PURPOSE

Continuously improve the writing/production system itself — engines, prompts, programs, QA, audio/visual workflows and cross-AI handoffs — without silently changing canon or rewriting locked work from taste.

This engine learns from production evidence. It does not grant the model unrestricted authority to rewrite the system.

## LEARNING LOOP

`OBSERVE → CAPTURE SIGNAL → CLASSIFY → FIND EARLIEST FAILURE → PROPOSE MINIMAL SYSTEM PATCH → TEST → COMPARE → ACCEPT/HOLD/REJECT → WRITE-THROUGH → REGRESSION → VERSION → HANDOFF`

## INPUT SIGNALS

High authority:
1. continuity/factual/professional error;
2. repeated blind-reader/listener/viewer evidence;
3. repeated performer/TTS failure on same function;
4. actual retention/drop/click/conversion data;
5. reproducible production/tool failure;
6. repeated cross-project defect;
7. independent specialist review with concrete evidence.

Lower authority:
8. one expert opinion;
9. one AI opinion;
10. isolated taste.

Repeated AI agreement is not independent validation when models share the same source/assumption.

## DELTA-SYNC INPUTS

On any material project-relevant turn, when available:
- current Google Drive CURRENT/authority docs;
- GitHub main/current production files;
- File Library/reference books;
- persisted outputs from adjacent project chats;
- approved Claude/Grok/other-AI reviews;
- prior compliance/pickup/experiment ledgers.

Do not treat inaccessible chat-only memory as authority. If a result exists only in an unpersisted neighboring conversation, status = DISCOVERY_ONLY until written through and verified.

## ISSUE CLASSIFICATION

FATAL — breaks causality, motivation, climax, canon, legal/professional truth, consent, release integrity.
MAJOR — weak opposition, passivity, fake stakes, repeated emotional function, voice collapse, systematic production defect.
MEDIUM — local pacing, micro-beat repetition, unclear cue, weak line, inefficient prompt/program step.
POLISH — taste/rhythm/style without demonstrated production harm.

## EARLIEST-FAILURE LAW

Do not patch downstream symptoms first.

Examples:
- bad chemistry may be casting/performance, not text;
- confusing clue may be mix/device translation, not exposition;
- repetitive dialogue may be scene function, not wording;
- poor model output may be router/context selection, not the specialist prompt;
- expensive production may be bad sampling policy, not tool quality.

Always identify the earliest layer that produced the defect.

## PATCH CONTRACT

Every proposed improvement must declare:
- problem/evidence;
- affected layer;
- exact artifact/version;
- protected invariants;
- minimal proposed change;
- success test;
- regression test;
- rollback path;
- whether canon changes (normally NO).

## EXPERIMENT LAW

For non-obvious improvements, compare:
A — current production standard;
B — candidate change.

Hold source material constant where possible.
Do not change three mechanisms at once and claim causality.

Record:
- test sample;
- conditions;
- metric/qualitative gate;
- outcome;
- side effects;
- decision.

## ACCEPTANCE

ACCEPT when the candidate:
- fixes the demonstrated defect;
- does not introduce FATAL/MAJOR regression;
- is simpler or more reliable at equal quality, or materially better at acceptable cost;
- survives the relevant medium/device/human gate where applicable.

ACCEPT WITH MODIFICATION when the mechanism is useful but implementation overreaches.

HOLD FOR TEST when evidence is insufficient.

REJECT when it duplicates existing authority, breaks protected invariants, increases complexity without measurable value, or solves a taste preference instead of a production defect.

## WRITE-THROUGH LAW

An accepted system improvement is not complete until:
1. current authority doc is updated;
2. executable prompt/program/router is updated;
3. compliance/experiment ledger records the decision;
4. superseded version is marked;
5. GitHub and Google Drive are synchronized where both are authorities;
6. next-chat handoff/current-state index points to the new version.

No silent improvement that lives only in one conversation.

## PROMPT IMPROVEMENT RULE

Do not endlessly grow prompts.

When adding a new mechanism, decide whether it belongs in:
- global router;
- specialized runtime;
- short inheritance header;
- audit gate;
- reference mechanism bank;
- project-specific prompt.

Prefer inheritance and routing over duplicating 2,000 words into every prompt.

Periodically remove:
- duplicated rules;
- obsolete versions;
- contradictory language;
- checks that never change decisions;
- expensive steps with no evidence value.

## MULTI-AI RULE

Use models by role, not by brand authority:
- Primary Integrator;
- Structural Adversary;
- Cold Reader/Retention Adversary;
- Specialist Reviewer;
- Production/Tool Specialist.

Each external AI must receive the same locked source/version when being compared.
Separate DIAGNOSIS from PROPOSED FIX.
No model vote determines canon.

## SELF-IMPROVEMENT BOUNDARIES

The engine may improve methods automatically within WORKING production state.
It may not silently:
- change Founder-approved canon;
- reopen a locked book without evidence;
- change final story resolution;
- add franchise lore;
- spend paid credits;
- publish/release;
- overwrite a verified authority with a stale branch.

## CONTINUOUS QUESTION SET

After meaningful work ask internally:
1. What failed or cost too much?
2. Was the earliest failure writing, routing, context, prompt, model, performance, mix, tool or test design?
3. Did an existing rule already cover it?
4. Is this project-specific or universal?
5. What is the smallest reusable mechanism?
6. What evidence would falsify the improvement?
7. Where must it be persisted so every future chat inherits it?

## FINAL PRINCIPLE

**The system learns from completed work and external evidence. It does not confuse more rules with more quality.**
