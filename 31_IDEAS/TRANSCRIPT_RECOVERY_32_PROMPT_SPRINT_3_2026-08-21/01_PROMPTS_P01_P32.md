# SPRINT 3 — 32 PROMPTS — TRANSCRIPT RECOVERY OPERATIONALIZATION

Global envelope for every prompt: fresh-read current authority first; reuse stronger sibling work; no transcript-as-canon promotion; no fabricated Founder/provider/human/market evidence; persist disposition even when BLOCKED; prefer extension/dedupe over another top-level engine.

## P01 — Fresh Recovery Frontier Rebase
Inventory the exact CURRENT, candidate, merged and open recovery/self-improvement surfaces. Separate verified current first-pass extraction, candidate semantic reconciliation, registry shards, merged Cycle-2 work and open sibling PRs. Output the true frontier and do-not-repeat list.

## P02 — Cross-Sprint Semantic Dedupe
Compare prior transcript Sprint 2, PR #67, merged PR #77 and open PR #78 by mechanism rather than filename. Classify each relevant mechanism as CURRENT / CANDIDATE / DUPLICATE / SUPERSEDED / UNIQUE / EXTERNAL-GATED. Do not merge by model agreement.

## P03 — Recovery Authority Surface Map
Build one authority/evidence map for recovery: Founder instruction, 18B, v1 extractor, SI-0009 candidate, registry-family pointer, project source-of-truth, Drive/GitHub readback, next-action resolver. Define what each surface may and may not decide.

## P04 — Missing-Gate Analysis
Identify the smallest set of unresolved gates between verified first-pass extraction and production-grade recovery. Rank by causal necessity and information value. Explicitly decide whether another parser upgrade is actually the bottleneck.

## P05 — Source Completeness Classifier
Design a fail-closed completeness contract separating: supplied corpus fully processed, original conversation proven complete, partial export, unknown completeness, multi-transcript bundle. Prevent `input_tail_processed=true` from being misread as proof that the old conversation itself was complete.

## P06 — Multi-Transcript Bundle Splitter Contract
Define how a pasted bundle containing several conversations is partitioned before semantic recovery. Require source identity, conversation boundaries when known, UNKNOWN when not knowable, and no invented missing turns.

## P07 — Multi-Project Partition Contract
Design project partitioning for one transcript that contains books, audio, engine, research and business lines. Define project identity, evidence scope, cross-project references and universalization rules.

## P08 — Cross-Project Leakage Red Team
Attack the partition contract with cases where the same character name, file title, engine mechanism or phrase appears in multiple projects. Produce fail-closed leakage rules and fixture cases.

## P09 — Chronology + Supersession Resolver
Define how recovered directives/artifact claims are ordered and superseded. Newer timestamp alone must not outrank higher authority. A direct Founder instruction may still be superseded by a later direct Founder instruction; assistant paraphrase cannot supersede either.

## P10 — Artifact Identity / Same-Name Ambiguity
Define identity rules for multiple files with the same visible title, copies of old docs uploaded later, renamed artifacts and branch copies. Require provider/file IDs, hashes or durable locators before declaring identity.

## P11 — SAVED / CREATED / UPDATED Claim Evidence Contract
For every transcript claim that something was saved, created, moved or updated, define required evidence and terminal states VERIFIED / NOT_FOUND / CONFLICT / UNKNOWN / STALE_COPY. A model sentence never satisfies the claim.

## P12 — Founder LOCK / Approval Claim Contract
Define evidence needed for Founder Lock, approval, branch selection or rejection. Distinguish direct Founder language from assistant paraphrase, inferred approval and silence. Fail closed on ambiguity.

## P13 — Test PASS / Runtime Claim Contract
Define evidence needed for automated PASS: exact source identity, command or harness, test output, exit status and version/commit. Separate source inspection from runtime execution and unit tests from production proof.

## P14 — Provider / Human / Market Evidence Firewall
Build one matrix for render/provider output, human reader/listener/editor signal, specialist review and market behavior. Define impossible substitutions: dry-run != live render; model review != Human Signal; predicted market score != observed behavior.

## P15 — UNKNOWN + CONFLICT as First-Class States
Define when UNKNOWN or CONFLICT must block ingestion completion, when they may be non-material, and how materiality is recorded without using convenience to downgrade uncertainty.

## P16 — Secret / Sensitive Persistence Firewall
Define redaction and non-persistence requirements for API keys, passwords, tokens, private credentials and other secrets found in recovery corpus. Preserve enough provenance to explain the omission without writing the secret into ledgers.

## P17 — Transactional Recovery Write Manifest
Design a write transaction object for chat-only candidate persistence and pointer updates: expected target identity, pre-state hash/version, mutation intent, reversibility, idempotency key, write result, readback result and rollback path.

## P18 — Readback / Rollback Gate
Define how partial Drive/GitHub writes are detected and repaired. Recovery cannot be COMPLETE merely because an API call returned success; accepted material writes require readback against intended state.

## P19 — Recovery Idempotency Contract
Define dedupe keys so rerunning the same corpus does not recreate chat-only candidates, duplicate verification tasks or repeat already committed writes. Handle source hash changes and corrected exports.

## P20 — Source Mutation + Resume Gate
Design chunk/resume rules for very large transcripts. If source SHA or ordered chunk lineage changes, previous checkpoints cannot silently resume. Specify allowed resume, forced restart and partial salvage states.

## P21 — Concurrent Sibling Write Collision
Model two dialogs recovering/advancing related state concurrently. Define stale-write detection, branch/shard strategy, rebase requirement and fail-closed behavior; prohibit force overwrite of newer authority.

## P22 — Registry Shard / Compaction Transaction
Evaluate current base+extension registry family. Define deterministic compaction prerequisites, uniqueness validation, input/output hashes, rollback and pointer switch. Candidate visibility must not become candidate promotion.

## P23 — Adversarial Recovery Fixture Catalog
Create a fixed catalog covering false saved claims, false LOCK, stale PASS, missing tail, mixed projects, same-name files, duplicated chat-only work, secret leakage, source mutation, provider/human/market claim inflation and concurrent write races.

## P24 — Synthetic Large-Corpus Fixture Strategy
Design large synthetic/mutated fixtures for parser/reconciliation stress without pretending they are production evidence. Include known ground truth and expected fail-closed outcomes.

## P25 — First Real Large Transcript Pilot Protocol
Define the exact end-to-end production pilot for the first genuinely large exported/pasted prior AI conversation. If no ingestable corpus exists, mark execution BLOCKED_REAL_CORPUS rather than substitute a synthetic one.

## P26 — Connector Verification Adapter Contract
Define provider-neutral verification adapters for GitHub and Google Drive claims: locator resolution, identity, content/readback, ambiguity, permissions and not-found semantics. Do not claim adapters are implemented merely because the contract exists.

## P27 — Recovery → Next-Action Handoff Contract
Define the boundary between recovery completion and ordinary production continuation. `INGESTION_COMPLETE` may permit handoff but must not bypass Founder, human, provider or other real gates.

## P28 — Learning Harvest Without Canon Leakage
Define what recovered mechanisms/failures can enter the Learning Ledger / Improvement Registry and what must remain project-specific. Require provenance, dedupe and lifecycle state.

## P29 — Founder Question Minimizer
Design a question gate: ask Founder only for irreducible high-authority choice, not for recoverable state, file location, ordinary duplicate classification or evidence the connected tools can verify.

## P30 — Repeated 32→64 Cycle Dedupe Audit
Audit the repository pattern of multiple parallel 32→64 sprints. Identify genuine information gain versus duplicated mechanism generation, branch/WIP debt and stale-base risk. Produce a cycle-level dedupe rule.

## P31 — Marginal Information Gain Stop Gate
Define when another research/prompt cycle should stop because the next decisive dependency is real external evidence or implementation, not more prompts. Founder explicit instruction can authorize a cycle, but the system must still label low-information work honestly.

## P32 — Promotion / Hold Decision + Roadmap
Integrate P01–P31. Decide what can be accepted now, what stays candidate, what is blocked, what should be pruned, and the exact next real gates. Derive the next 64 prompts from evidence, not mechanical doubling alone.
