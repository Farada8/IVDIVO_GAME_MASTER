# IVDIVO — SELF-IMPROVEMENT META ENGINE v2.0

**Status:** CURRENT CANDIDATE FOR UNIVERSAL OPERATIONAL AUTHORITY — FOUNDER DIRECTIVE  
**Version:** 2.0  
**Established:** 2026-08-21  
**Scope:** the whole IVDIVO production system, with first priority on writing strong books and transforming locked books into high-quality audio novels.  
**Supersedes for lifecycle/orchestration purposes:** `17_SELF_IMPROVEMENT_ENGINE_v1.0.md` after promotion/readback. v1.0 remains historical/base evidence.  
**Does not supersede:** story/book canon, current Writing Studio authority, current Audio Production authority, project-specific source-of-truth, Human Signal or provider evidence.

---

## 0. FOUNDER OBJECTIVE

IVDIVO must become a cumulative production intelligence rather than a collection of disconnected conversations, files and experiments.

The engine must continuously improve what matters most:

1. **WRITE BETTER COMPLETE BOOKS.**
2. **TURN LOCKED BOOKS INTO BETTER AUDIO NOVELS / DRAMATIZED AUDIO.**
3. **INCREASE PRODUCTION RELIABILITY, SPEED, REUSE AND COST-EFFICIENCY WITHOUT LOWERING QUALITY.**
4. **BUILD BETTER ENGINES, PROMPTS, PROGRAMS, ROUTERS, QA AND MULTI-AI WORKFLOWS.**
5. **STUDY / RESEARCH / LEARN FROM BOOKS, PROJECTS, FAILURES, SUCCESSFUL PILOTS, HUMAN SIGNAL, MARKET SIGNAL AND NEW TOOLS.**
6. **APPLY VERIFIED IMPROVEMENTS ACROSS ALL RELEVANT IVDIVO DOMAINS.**
7. **SIMPLIFY OR DELETE OBSOLETE COMPLEXITY.**

The system is allowed to improve itself, but it may not override higher authority or starve primary production.

---

# 1. PRIMARY PRIORITY STACK

The Self-Improvement Engine uses an ordered objective stack rather than one blended numeric score.

### P0 — AUTHORITY / SAFETY / INTEGRITY
Protect Founder instruction, canon, source hashes, project truth, human-evidence boundaries, provider truth and rollback capability.

### P1 — STORY / BOOK QUALITY + COMPLETION
Improve causality, protagonist agency, character specificity, emotional impact, dialogue, pacing, mystery/romance/world integration, continuity, originality and completed resolution.

A beautifully engineered system that produces weak or unfinished books is a failure.

### P2 — BOOK → AUDIO NOVEL QUALITY
Preserve locked story while maximizing performance, comprehension, emotional force, listening rhythm, voice differentiation, sound dramaturgy, clue fidelity, mix quality and release reliability.

### P3 — PRODUCTION PERFORMANCE
Reduce duplicated work, stale work, unnecessary regeneration, manual nudges, provider waste, repair cycles, cycle time and context loss while preserving P0–P2.

### P4 — ENGINE / TOOL / PROMPT QUALITY
Improve orchestration, repair logic, schemas, software, routing, multi-AI delegation, test coverage, observability, automation and reproducibility.

### P5 — RESEARCH / LEARNING
Continuously discover new mechanisms, tools, craft knowledge, scientific/technical facts, audience evidence and production practices that can improve P1–P4.

### P6 — BROADER IVDIVO CAPABILITY
Visual production, marketing/packaging, publishing support, business/process tooling and other creative/operational domains.

**Priority law:** lower priorities may support higher priorities; they may not silently sacrifice them.

# 2. THREE COUPLED LOOPS

## LOOP A — BOOK PRODUCTION LOOP — PRIMARY

`FOUNDER RAW / IDEA -> STORY DISCOVERY -> REFERENCE INTELLIGENCE -> PREMISE/ENGINE COMPETITION -> STORY CORE -> CHARACTER -> RELATIONSHIP/MYSTERY/WORLD -> ARCHITECTURE -> CAUSAL MAP -> STORY GATE -> SCENE CONTRACTS -> PROSE -> DEVELOPMENT -> RED TEAM -> P51/P52/P53 REGRESSION -> READER ADVOCATE -> CONTINUITY / SOURCE-DISTANCE -> LINE -> FINAL STORY GATE -> HUMAN/EXTERNAL SIGNAL WHERE REQUIRED -> STORY LOCK`

The Self-Improvement Engine observes this loop. It does not replace it.

## LOOP B — LOCKED BOOK → AUDIO NOVEL LOOP — SECOND PRIMARY

Current controlling authority remains `CURRENT_IVDIVO_AUDIO_PRODUCTION_AUTHORITY.md`.

High-level transformation:

`STORY LOCK -> AUDIO PROJECT AUTHORITY + SOURCE HASH -> DELIVERY MODE / TEXT PROTECTION -> SPOKEN UNIT / SCENE MAP -> LISTENER CONTRACT -> DRAMATIC FORCE MAP -> AUDIO STAGING -> CAST / VOICE BINDING -> PERFORMANCE DIRECTOR SCORE -> PAUSE / BREATH / LISTENING / OVERLAP -> MICROPHONE CHOREOGRAPHY / PROXIMITY -> ACOUSTIC / POA / STEREO INTENT -> FOLEY / SFX / AMBIENCE / MUSIC -> RENDER BLOCKS -> PROVIDER DRY RUN -> PROVIDER PREFLIGHT -> LIVE CANARY / CASTING CASCADE -> HARD PILOT -> PARALLEL PRODUCTION -> ALIGNMENT / TIMELINE -> MIX -> MASTER -> MACHINE QC -> HUMAN LISTEN / MANUAL REVIEW -> SELECTIVE REPAIR -> RELEASE GO/NO-GO -> MASTER LOCK`

Audio defects stay in audio unless evidence proves the protected text/story is the earliest failed layer.

## LOOP C — SELF-IMPROVEMENT / LEARNING LOOP — EMBEDDED

`OBSERVE -> CAPTURE -> DEDUPE -> DIAGNOSE -> RESEARCH -> DEVELOP -> PILOT -> RED TEAM / REGRESSION -> PROMOTE -> APPLY -> VERIFY -> MONITOR -> RETAIN / NARROW / MERGE / ROLLBACK / SUPERSEDE`

Loop C exists to improve A and B first, then the rest of IVDIVO.

# 3. OBSERVABILITY: WHAT THE ENGINE LEARNS FROM

The engine harvests evidence from:
- sibling Project conversations;
- current GitHub/Drive artifacts;
- File Library / books / scripts / craft/research sources;
- Story Engine Source Passports / Mechanism Banks / Crosswalks;
- Development, Red Team, Reader Advocate and continuity failures;
- repeated targeted/global repairs;
- successful scenes/books and why they worked;
- audio canaries, casting evidence, render failures, re-render causes, QC and listening notes;
- provider/API/tool changes;
- actual Claude/Grok/GPT/other-model reviews with provenance;
- actual human readers/listeners/editors;
- real market/publisher/platform data when available;
- cycle-time / cost / duplication / stale-work signals;
- the engine's own errors and bureaucracy.

Unavailable evidence remains `UNKNOWN / NOT_RECEIVED`.

# 4. PROBLEM-MINING ENGINE

Do not wait only for humans to invent improvements.

At meaningful milestones, inspect evidence for recurring problems:
- repeated FATAL/MAJOR type;
- same repair performed more than once;
- same clarification requested repeatedly;
- repeated context/state loss;
- duplicated prompts/routers;
- project-specific mechanism repeatedly useful elsewhere;
- provider spend with high rejection/re-render rate;
- scene/dialogue pattern repeatedly flagged as generated/generic;
- book-to-audio adaptation friction;
- tool/API/manual step repeatedly slowing production;
- current rules that no longer change decisions.

Convert recurring patterns into `BUG_OR_FAILURE_PATTERN` or `IMPROVEMENT_CANDIDATE` records.

# 6. BEST-CANDIDATE ROUTER

The engine does not develop ideas in arrival order.

For active candidates compare qualitatively:
- relevance to the current production bottleneck;
- effect on P1/P2 before P3–P6;
- potential impact;
- recurrence/systemic reach;
- evidence strength;
- transferability;
- effort;
- regression risk;
- reversibility;
- urgency;
- current dependency unblocking value.

Priority classes:

### A — PRODUCTION BLOCKER / MAJOR LEVER
A system defect blocks or materially damages current book/audio production, or a verified improvement unlocks a major frontier.

### B — HIGH REUSE / HIGH QUALITY LEVER
Recurring mechanism likely to improve multiple books/projects or reduce recurrent MAJOR defects.

### C — DOMAIN OPTIMIZATION
Useful within one recurring domain: audio, romance, Smith, Orbital Youth, visual, market, etc.

### D — EXPLORATORY / RESEARCH
Potentially valuable but weak evidence or no immediate bottleneck.

### E — LOW VALUE / DUPLICATE / RITUAL
Merge, narrow, archive or reject.

No fake precision score is required.

# 7. WIP / ANTI-BEDLAM LAW

Self-improvement itself must not become conversational chaos.

Default meta-work limits:
- one PRIMARY improvement candidate actively being integrated at a time;
- up to two independent bounded pilots/research candidates in parallel when they do not share mutable authority;
- unlimited captured backlog, but every item must have state/next action/hold trigger.

The current book/audio production frontier outranks meta-work unless:
- a system FATAL/MAJOR blocks production;
- the improvement is a direct prerequisite;
- the Founder explicitly switches focus to system development.

# 8. RESEARCH ENGINE

Research is problem-driven, not endless browsing.

For each research candidate define:
1. decision to improve;
2. current uncertainty;
3. evidence needed;
4. best source classes;
5. stopping rule;
6. abstraction target;
7. pilot/application target.

Research sources may include craft books, novels, scripts, academic/technical sources, provider documentation, current tools, market/platform information and external specialists.

Output must separate:
`SOURCE FACT / ABSTRACT MECHANISM / INFERENCE / HYPOTHESIS / TEST / DECISION`.

Reference law:
`REFERENCE -> ABSTRACT MECHANISM -> REMOVE DISTINCTIVE CONTENT -> COMBINE INDEPENDENT SOURCES WHEN USEFUL -> TRANSFORM THROUGH ACTIVE PROJECT -> SOURCE-DISTANCE CHECK`.

Research is complete only when it changes a decision, closes uncertainty, creates a testable candidate, or is explicitly rejected/held.

---

# 9. DEVELOPMENT / EXPERIMENT ENGINE

Every serious candidate must become falsifiable enough to test.

Development contract:
- problem/root cause;
- proposed mechanism;
- causal explanation;
- target layer;
- baseline/current method;
- expected improvement;
- failure modes;
- protected invariants;
- smallest useful pilot;
- evidence to collect;
- acceptance/rejection gate;
- rollback path;
- descendants requiring regression.

Preferred implementation route:
`SANDBOX -> FIXTURE -> ADVERSARIAL TEST -> LIMITED REAL PILOT -> REGRESSION -> PROMOTION`.

No broad self-modification from an attractive idea.

# 10. BOOK-WRITING IMPROVEMENT SENSORS

At Story Core / Architecture / prose milestones, capture patterns rather than only patching symptoms.

Track at minimum:
- FATAL/MAJOR type and earliest failed layer;
- number of repair cycles before GREEN;
- protagonist-passivity recurrence;
- weak midpoint / climax / resolution recurrence;
- exposition/world-lore overload;
- P51 voice collisions and shared constructions;
- P52 flat emotional range;
- P53 authority/relationship routing errors;
- character-functionality vs specific-person failures;
- reader "homework" / comprehension issues;
- continuity contradictions;
- source-distance/originality risk;
- repeated line-edit patterns that originate upstream;
- which mechanisms consistently prevent defects.

A repeated downstream symptom must become an upstream improvement candidate when evidence supports the root cause.

---

# 11. BOOK → AUDIO IMPROVEMENT SENSORS

Track at minimum:
- adaptation/spoken-unit ambiguity;
- text-protection violations;
- voice audition rejection causes;
- direction-change responsiveness;
- pair/ensemble failures;
- long-form fatigue issues;
- pronunciation/identity drift;
- clue/SFX/musical-fact inconsistency;
- number/cause of regenerated blocks;
- provider/API failures;
- alignment/timeline errors;
- mix/master/QC failure types;
- manual review defects;
- listening comprehension/emotional-performance failures;
- cost/credit waste caused by preventable upstream mistakes.

Promote reusable audio mechanisms only after stripping project-specific voices, clue chains, melodies and story facts.

---

# 12. PRODUCTIVITY / COST IMPROVEMENT ENGINE

Optimize only after quality/integrity constraints are explicit.

Look for:
- duplicated reading/search;
- repeated context reconstruction;
- unnecessary full regeneration;
- serial execution of dependency-independent work;
- missing templates/schemas;
- expensive live-provider calls before zero-cost preflight/canary;
- work performed before authority/source hashes are resolved;
- manual data transfer that can be safely automated;
- repeated outputs that should become reusable artifacts;
- prompts that are too broad and create correction cycles.

Preferred gains:
`LESS DUPLICATION + EARLIER ERROR DETECTION + SELECTIVE REPAIR + REUSE + PARALLEL SAFE BRANCHES + CANARY BEFORE SCALE`.

Speed gained by weakening story/audio quality is a regression, not an improvement.

---

# 13. ENGINE / PROMPT / SOFTWARE IMPROVEMENT

Candidate sources:
- recurring manual operation;
- repeated schema mismatch;
- stale-state/concurrency bug;
- duplicated prompts;
- repair bug;
- provider/API contract change;
- missing test;
- weak observability;
- non-reproducible handoff.

Required for code/tool promotion where applicable:
- deterministic tests;
- negative/adversarial tests;
- existing regression suite remains green;
- fail-closed invalid state handling;
- cold/reproducibility test for packaged artifacts;
- rollback or previous-current pointer;
- no secret/API-key persistence.

Higher automated test count alone does not prove literary or production superiority.

---

# 14. MULTI-AI SELF-IMPROVEMENT CELL

Different AI systems may be used as orthogonal specialists, never as parallel canons.

Recommended bounded roles:
- **Scout:** finds deltas, new tools, new evidence;
- **Researcher:** source-grounded mechanism extraction;
- **Designer:** develops candidate mechanism;
- **Independent Red Team:** attacks candidate without inheriting proposer conclusions where possible;
- **Implementer:** applies accepted candidate to bounded targets;
- **Regression Verifier:** checks what broke;
- **Reader/Market Specialist:** downstream audience/product evidence;
- **Reconciler/Integrator:** final disposition against authority.

External outputs require provenance and disposition:
`ACCEPT / ACCEPT_WITH_MODIFICATION / HOLD_FOR_TEST / REJECT`.

No model vote canon.

# 15. PROMOTION / DEPLOYMENT ENGINE

Promotion route:
`PROMOTION_REVIEW -> SELECT SCOPE -> APPLICATION MAP -> SNAPSHOT/PREVIOUS CURRENT -> APPLY -> READBACK -> TEST/REGRESSION -> UPDATE CURRENT POINTERS -> VERIFIED_CURRENT`.

Promotion levels:
- PROJECT;
- BOOK/SERIES;
- DOMAIN;
- UNIVERSAL.

Promotion without application is incomplete.
Application without verification is `APPLIED_UNVERIFIED`.

A universal upgrade must update every materially affected controlling surface, for example:
`AUTHORITY / ROUTER / CONFIG / PROMPT / CODE / SCHEMA / TESTS / HANDOFF / CURRENT STATE / DRIVE MIRROR`.

# 16. FEEDBACK LOOP FROM PRODUCTS

Finished books and released audio are experiments in the real world.

When actual evidence becomes available, ingest:
- reader/listener drop-off;
- comprehension confusion;
- emotional peaks/flat sections;
- reviews/comments;
- completion/retention where platform data exists;
- conversion/purchase behavior where real;
- publisher/editor/agent notes;
- production economics;
- rework burden.

Never fabricate these signals.

Convert repeated real signals into improvement candidates and update confidence in existing mechanisms.

# 17. SELF-IMPROVEMENT OF THE SELF-IMPROVEMENT ENGINE

This engine is not exempt from its own rules.

Any proposed change to this engine must enter the same registry and pass:
`PROBLEM -> CANDIDATE -> PILOT -> RED TEAM -> PROMOTION -> APPLY -> VERIFY`.

It may not bypass gates by declaring itself "self-improving".

Monitor for:
- too much meta-work;
- candidate backlog bloat;
- duplicate rules;
- false promotion;
- useful ideas stuck too long;
- improvement work that does not affect production;
- excessive context/search overhead;
- routing conflicts.

---

# 18. KNOWLEDGE COMPACTION / PRUNING

Learning must compress knowledge, not only add files.

Periodically reconcile:
- duplicate prompts;
- superseded routers;
- repeated mechanisms with different names;
- old candidate branches;
- reference abstractions now covered by stronger mechanisms;
- rules that no longer change decisions.

Disposition:
`KEEP / MERGE / NARROW / SUPERSEDE / ARCHIVE / DELETE_FROM_CURRENT`.

One current authority per function whenever possible.

---

# 19. FAILURE / SUCCESS MEMORY

Maintain reusable lessons from both defects and successes.

For meaningful failure:
`SYMPTOM -> ROOT CAUSE -> EARLIEST FAILED LAYER -> FIX -> ACCEPTANCE TEST -> REUSABLE PREVENTION MECHANISM`.

For meaningful success:
`OUTCOME -> WHICH DECISIONS/MECHANISMS CONTRIBUTED -> ALTERNATIVE EXPLANATIONS -> WHERE IT GENERALIZES -> PILOT ELSEWHERE`.

Do not learn only from errors.

---

# 20. OPERATING CADENCE

The engine runs synchronously during active work sessions/milestones; it does not pretend to execute invisibly when no session/task is running.

Mandatory bounded sweep:
- at substantial project boot;
- at Story Gate / major Development or Red Team milestones;
- at Story Lock before audio handoff;
- after audio hard pilot;
- after release QC/master lock;
- after meaningful human/market/external feedback;
- after a recurring production defect;
- before inventing a new universal engine/router/prompt.

Optional scheduled research/review may be added through explicit automation, but autonomous background work must never be falsely claimed.
