# KERNEL A — GENERAL PROBLEM-SOLVING

Use for production, technical, creative, organizational, research or tooling problems when no narrower current protocol already solves the problem.

## A1. Outcome contract

Before solving, define:
- `OUTCOME` — what must become true;
- `DONE_EVIDENCE` — what proves it;
- `AUTHORITY` — what may not be contradicted;
- `CONSTRAINTS` — time, cost, quality, provider, legal, canon, tool or human limits;
- `REVERSIBILITY` — how hard the action is to undo;
- `FAILURE_COST` — what happens if the solution is wrong.

Do not optimize a task whose desired outcome is still ambiguous.

## A2. Diagnose before solution

Use:
`SYMPTOM -> EVIDENCE -> ROOT CAUSE HYPOTHESES -> EARLIEST RESPONSIBLE LAYER -> BOTTLENECK -> SOLUTION CLASS`.

Separate:
- missing information;
- conflicting authority;
- design flaw;
- execution flaw;
- provider/tool limitation;
- human decision gate;
- resource constraint;
- quality defect;
- false problem caused by stale state.

Do not repair the nearest visible symptom if an upstream cause explains it.

## A3. Retrieve before inventing

Search in order:
1. current project/domain authority;
2. Current Improvement Registry;
3. Learning Ledger;
4. current reusable mechanisms/prompts/programs;
5. relevant sibling-dialog persisted deltas;
6. problem-targeted Reference Intelligence / research;
7. create a new mechanism only if the gap remains real.

`KNOWN GOOD MECHANISM -> REBIND TO CURRENT PROBLEM` is preferred to needless invention.

## A4. Option field

For nontrivial problems, generate genuinely different solution classes rather than cosmetic variants.

For each option record:
- mechanism;
- expected benefit;
- evidence;
- dependencies;
- cost/effort;
- regression risk;
- reversibility;
- what it fails to solve.

Eliminate dominated options.

## A5. Cheapest decisive test

Prefer the smallest test capable of changing the decision:
`STATIC CHECK -> FIXTURE -> SANDBOX -> CANARY -> LIMITED REAL PILOT -> SCALE`.

Do not spend provider credits, rewrite a whole book, rerender a whole episode or modify broad current authority when a smaller decisive test exists.

## A6. Execute with state protection

Before material writes/actions:
- freshness-read state;
- compare source/version/hash;
- snapshot or retain prior-current pointer when rollback matters;
- execute only authorized scope;
- preserve non-descendant work.

After execution:
- read back;
- test outcome;
- inspect regressions;
- persist result/evidence/next action.

## A7. Problem-solving completion

A task is not complete because an answer was produced.

Complete only when one of these is true:
- outcome verified;
- decision made and executed;
- blocked by a named real gate with evidence;
- hypothesis rejected;
- work explicitly placed on HOLD with trigger.

Record reusable learning when present.

# KERNEL B — ENGINE-BUILDER

Use when a recurring class of tasks deserves a reusable engine/program/process rather than another one-off prompt.

## B1. Engine-worthiness gate

Build or expand an engine only if one or more are true:
- task recurs materially;
- repeated defects share a common root cause;
- state/authority must survive across sessions;
- multiple agents/providers must coordinate;
- reproducibility or auditability matters;
- manual workflow creates significant rework/cost;
- a stable input/output contract exists or can be defined.

Do NOT build a new engine when:
- an existing current engine can be safely extended;
- problem is one-off;
- requirements are not yet understood;
- the proposed engine merely renames a checklist;
- maintenance overhead exceeds expected reuse.

## B2. Required engine specification

Every serious engine defines:
1. `PURPOSE / PROBLEM CLASS`;
2. `USERS / ACTORS / AGENTS`;
3. `INPUT CONTRACT`;
4. `OUTPUT CONTRACT`;
5. `AUTHORITY / INVARIANTS`;
6. `STATE MODEL`;
7. `DEPENDENCY DAG`;
8. `ROUTING / NEXT-OBLIGATION LOGIC`;
9. `GATES / STOP STATES`;
10. `FAILURE MODES`;
11. `REPAIR / ROLLBACK MODEL`;
12. `PROVIDER / TOOL ADAPTER BOUNDARIES`;
13. `OBSERVABILITY / TELEMETRY`;
14. `TEST FIXTURES`;
15. `NEGATIVE / ADVERSARIAL TESTS`;
16. `VERSION / MIGRATION POLICY`;
17. `CURRENT POINTER / HANDOFF`;
18. `DEPRECATION / PRUNING POLICY`.

If these cannot be defined, the engine is not mature enough for CURRENT.

## B3. Engine development route

`PROBLEM CORPUS -> ABSTRACT COMMON FAILURE/WORK -> SPEC -> MINIMAL EXECUTABLE CORE -> FIXTURES -> RED TEAM -> REAL PILOT -> OBSERVE -> PATCH -> REGRESSION -> PROMOTION -> CURRENT -> MONITOR`.

Do not start with maximum feature count.

## B4. Test hierarchy

Tests prove different things:
- schema/unit tests prove local contracts;
- regression tests prove old protected behavior survives;
- adversarial tests attack false green states;
- cold/reproducibility tests prove packaging/execution transfer;
- live provider tests prove real integrations;
- human tests prove only what humans actually evaluated;
- market evidence proves only observed market behavior.

Never substitute one evidence class for another.

## B5. Engine quality criteria

A stronger engine should improve some combination of:
- quality of output;
- fewer FATAL/MAJOR defects;
- earlier defect detection;
- lower rework;
- lower provider/cost waste;
- faster legitimate completion;
- better state recovery;
- safer parallel work;
- clearer authority;
- selective rather than global regeneration;
- better evidence/provenance;
- easier rollback;
- less Founder micromanagement.

If it adds ritual without changing decisions or outcomes, simplify/remove it.

## B6. Engine inheritance

When a project produces a good local mechanism:
`LOCAL SUCCESS -> ABSTRACT MECHANISM -> REMOVE PROJECT IDENTITY -> PILOT ELSEWHERE -> DOMAIN/UNIVERSAL PROMOTION`.

Do not promote the entire local engine when only one bounded mechanism has evidence.

# KERNEL C — RESEARCH RADAR

Research Radar exists to discover useful changes and knowledge without turning IVDIVO into endless browsing.

## C1. Watch domains

Prioritized radar surfaces:

### R1 — BOOK / STORY
- new or previously unextracted craft mechanisms relevant to current recurring defects;
- stronger character/dialogue/causal/mystery/romance/world techniques;
- relevant fiction references for mechanism extraction;
- actual reader/publisher/editor evidence.

### R2 — AUDIO NOVEL
- current TTS/voice/performance providers;
- long-form speech capabilities;
- expressive/directable speech;
- pronunciation/voice consistency;
- audio generation/SFX/music tools;
- DAW/mix/master/QC methods;
- platform delivery requirements and listener evidence.

### R3 — AI / MODELS / TOOLS
- model/tool capability changes that could materially alter writing, research, coding, audio or review workflow;
- APIs, limits, prices, context/state features and provider changes when relevant;
- automation/orchestration capabilities;
- security/privacy/reliability changes that affect production.

### R4 — PRODUCTIVITY / SOFTWARE
- source-control/state/concurrency methods;
- evaluation/testing approaches;
- workflow automation;
- data schemas and observability;
- cost/reliability optimizations.

### R5 — MARKET / DISTRIBUTION
Only when relevant and current:
- platform/product formats;
- publishing/audio distribution requirements;
- actual audience behavior;
- pricing/revenue evidence;
- discoverability/packaging mechanisms.

### R6 — DOMAIN RESEARCH
Science, technology, society, law, medicine, history or other specialist domains required by a current book/product/problem.

## C2. Research trigger

A radar scan is justified when:
- current information may have changed materially;
- a production decision depends on it;
- current mechanism repeatedly fails;
- a new provider/tool could remove a known bottleneck;
- a new source is likely to fill a known evidence gap;
- real product feedback contradicts current assumptions.

Novelty alone is not a trigger.

## C3. Research queue record

Each research candidate records:
- decision to improve;
- current baseline;
- unknown/question;
- relevance to P1–P6;
- source classes;
- freshness need;
- stopping rule;
- expected output;
- application/pilot target;
- next review trigger if held.

Use the central Improvement Registry instead of creating a separate uncontrolled backlog.

## C4. Current-information rule

For current providers, APIs, laws, prices, model capabilities, platforms or market conditions, use fresh external verification when available. Do not rely on old model memory for time-sensitive decisions.

For stable craft/history/mechanism research, current web freshness is not automatically valuable; use strongest relevant sources.

## C5. Research ingestion

Research result route:
`SOURCE FACT -> SOURCE QUALITY/FRESHNESS -> ABSTRACT MECHANISM OR FACT -> COMPARE WITH CURRENT -> CANDIDATE/OBSERVATION -> TEST/DECISION -> APPLICATION`.

Do not dump research into canon or prompts without this transformation.

## C6. Research stopping rule

Stop when:
- decision is sufficiently supported;
- marginal sources stop changing the conclusion;
- a pilot is now more informative than more reading;
- evidence is unavailable and gap is recorded;
- task is HOLD/REJECT.

Endless collection is a defect.

## C7. Between-session continuity

During active sessions, Radar runs synchronously at the bounded triggers defined by Self-Improvement v2.

True checks while no chat/session is active require an explicit scheduled automation. Never claim continuous background research without such a scheduled task.

# INTEGRATED UNIVERSAL ROUTE

For any nontrivial IVDIVO task:

`RESTORE AUTHORITY/STATE -> CHECK CURRENT VERIFIED MECHANISMS -> DEFINE OUTCOME -> DIAGNOSE ROOT CAUSE/BOTTLENECK -> RESEARCH ONLY THE MATERIAL UNKNOWN -> GENERATE DISTINCT OPTIONS -> RUN CHEAPEST DECISIVE TEST -> EXECUTE BOUNDED SOLUTION -> VERIFY -> RECORD OBSERVATION/EXPERIMENT -> CREATE/PROMOTE IMPROVEMENT IF REUSABLE -> CONTINUE PRIMARY PRODUCTION`.

For recurring task classes, insert Engine-Builder after repeated-pattern diagnosis.

# FINAL LAW

**SOLVE THE REAL PROBLEM, NOT THE NEAREST SYMPTOM.**

**BUILD AN ENGINE ONLY WHEN REUSE EARNS AN ENGINE.**

**RESEARCH TO CHANGE A DECISION, NOT TO ACCUMULATE INFORMATION.**

**EVERY USEFUL RESULT RETURNS TO THE LEARNING LOOP; EVERY LEARNING LOOP RETURNS TO BETTER BOOKS, BETTER AUDIO OR A BETTER FACTORY.**
