## Source-grounded architecture

The Commission's current DPP architecture has two distinct data planes:

1. **DPP Registry** — an EU indexing/registration service storing unique identifiers, registration data and high-level metadata; exact mandatory registration data depends on applicable Union legislation.
2. **Decentralised DPP payload** — detailed product information remains under the responsible economic operator or DPP service provider.

The Registry and its testing environment became operational on 20 July 2026. The testing environment is expressly intended for safe workflow exploration without affecting live data or real processes. Registration can be integrated via user interface or API, but this artifact does **not** log in, create an organisation, register a DPP, or claim API conformance.

## Preflight planes

### A. Applicability
Records a **declared fixture state** only: `KNOWN_IN_SCOPE`, `KNOWN_NOT_YET_IN_SCOPE`, or `UNKNOWN`. The tool does not decide legal applicability. Unknown applicability holds the case.

### B. Economic operator
Preflight requires an economic-operator identifier and role because the Commission architecture assigns DPP creation/maintenance/registration responsibilities to the relevant economic operator under applicable legislation.

### C. Product identity
A product identifier is required by this engineering contract. Commodity code is routed for imported-product fixtures because the Commission describes customs verification of a registered DPP and commodity code before release for free circulation.

### D. Linkage / decentralised payload
The fixture tracks the data-carrier type and the location of the decentralised DPP payload. These are implementation-readiness fields in this engineering model; they are not asserted to be an exhaustive live Registry API request schema.

### E. Supplier evidence
Every synthetic supplier record binds supplier ID, data point, value, source-evidence locator and freshness date. This is an evidence/provenance contract, not a legal requirement claim for every DPP data point.

### F. Product-specific mapping
`fixture_required_data_points` is deliberately named **fixture** required. It must come from a verified product-specific rule/data model before real use. The generic validator must never promote a guessed universal DPP field list.

### G. Registry boundary
The unique registration identifier generated by the Registry is treated as an **output**. A pre-registration fixture that claims it already has the Registry-generated identifier fails the boundary check.
